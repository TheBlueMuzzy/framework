Notes:
- Muzzy 2026-10-20: link codes last 7 days. How long a match is kept depends on the game ("async Scrabble-with-friends → 30, a live game I forget during chores → 7") → a per-game setting `keepMatchDays` (any number), asked at install time and changeable later.
- Plan-lint: only the old F61 / F59 / F60 line (Goops' session). No open P0/P1 bugs.
- F96 — the live host's FREE limits, checked 2026-10-20 (developers.cloudflare.com: durable-objects/platform/pricing, durable-objects/platform/limits, workers/platform/limits): Workers 100,000 requests/day, 10 ms CPU per request, 100 workers per account · Durable Objects 100,000 requests/day (alarm runs count as requests), 13,000 GB-s/day, SQLite 5 million rows read/day, **100,000 rows written/day** (each `setAlarm` = 1 row written), 5 GB stored per account, 1 GB per object (FAQ), 2 MB per row/value, 100 KB per SQL statement, 100 classes per account; limits reset 00:00 UTC, past one the operation fails. Fit: a link code ≈ 1 save row + 1 try-count row + at most 1 alarm set; a wrong guess = 1 row; the worker only sets an alarm when none is set or it's later. KV's free plan would allow only 1,000 writes/day — the reason for the SQLite object. Save codes are bound values (not in the SQL text), ≤ 300,000 characters, far under 2 MB; new codes stop at 900 MB stored (the 1 GB object).
- F96 judgement calls: (1) fetching a code does NOT delete it — a third device / a retry after full storage; "Delete my data" from either device ends it. (2) The cloud is its own small worker (`cloud/worker.ts` + `cloud/wrangler.json`, `<game>-saves`, port 1998), not inside a rooms game's party worker — a rooms deploy never touches saves; installed only with `--cloud`. (3) Uploads are limited too (`cloud.uploadsPerHour` 20) so one address can't fill the store. (4) Malformed typing ("hello") is refused without counting as a guess (it can't match anything). (5) Addresses only as a SHA-256 scramble, only for the hour. (6) No Cloudflare type package: the worker is a plain class with `fetch()` + `alarm()` and writes out the few shapes it uses (typechecks under Goops' `erasableSyntaxOnly`). (7) "Make a link code" with nothing saved yet says so instead of sending an empty code. (8) The Save code screen's body is now one ScrollArea (it's taller) — no UI kit change.
- F96 surprises: wrangler dev sets CF-Connecting-IP locally, so the guess limit really counts per address there too (curl and the browser shared 127.0.0.1's budget — the proof's 20-wrong run saw 9 + 11 because one earlier wrong try was the deleted code). The kit's style uppercases toasts (CSS) — Playwright's innerText reads them in capitals; compare textContent. The "didn't work" sentence says "7 days" from the game's config even on a TEST_KEEP_SECONDS server (expected: the test var is server-only).
- F96 review (helper, security; Claude fixed + tests, saves 151/151): ① guesses / uploads sent all at once all passed the limit (the check waited on the body before counting) → body + scramble first, then check-and-count with no wait (a 30-at-once test) · ② IPv6 counted per full address (2^64 per home) → counted per /64, plus a server-wide cap of 2,000 wrong guesses an hour · ③ the address hash had no secret (IPv4 could be reversed) → HMAC with a random secret the worker makes once and keeps · ④ fetching another device's code made this device forget its own → its own live code is kept, so Delete my data still reaches it. Verified fine: secure random codes with no bias, no overwrite on a clash, SQL placeholders, server-side size cap, delete needs the code.
- F100 — Cloudflare free-plan limits, checked 2026-10-20 (developers.cloudflare.com/durable-objects/platform/pricing + /platform/limits): SQLite-backed Durable Objects (the only kind on Free) get 100,000 rows written/day, 5 million rows read/day, 100,000 requests/day, 13,000 GB-s/day, 5 GB stored in all; 2 MB per key+value; an alarm handler may run 15 min. A key-value put = rows written, "deletes are counted as rows written", "each setAlarm() is billed as a single row written". Design: one key per room, saved once per change (a microtask batches everything in one go) and only if the packed JSON changed — taps, "sync" and refused moves write nothing; the alarm only moves when its time changes.
- F100 measured on the scratch Glyphtender (2 players → 2 bots playing it out): 94 saves + 88 alarm moves + 1 wipe ≈ 180 rows for a whole match → ~550 matches a day on Free. Biggest save 52 KB (2 MB allowed). The alarm moves on nearly every save (each bot step / turn clock is a new earliest timer) — if that ever matters, set the alarm only for room timers + the turn clock, not bot think-pauses.
- F100 proof (scratch .scratch/glyphtender-f100, e2e/f100-restart.mjs, wrangler on 3999 --persist-to .wrangler/state-f100, vite 5393): ALL PASSED — mid-match the server was stopped and started → both back in the same seats, same turn (draft, Bo to place), same version, turnEndsAt unchanged; the turn timer then ran out 67 ms after the saved end time (a fresh clock would have been ~16 s late); both left → bots finished → "game over" + storage wiped → after a restart the code answers no_room; keepMatchDays 0.0001 with the server off past it → Rejoin → "That match has ended".
- F100 judgement calls: only a match being PLAYED is kept (lobby and finished games are not — cheap to remake / nothing to return to). Every player is "away" after a restart (their sockets died), so a bot takes over after botTakesOverAfterMs unless they reconnect — PartySocket reconnected both in ~3 s. The keepMatchDays clock restarts on a move (a player's, a bot's, the game's timer), not on a seat changing hands. A match already past keepMatchDays when the room wakes is never loaded (no flash of a dead match). keepEmptyRoomMs stays for rooms that aren't kept (finished game nobody left, a host without storage, a state that isn't plain JSON). A state that isn't plain JSON is logged and kept in memory only (old behaviour) rather than refused. The installer asks for keepMatchDays after every fresh install too (the template's 7 is only a default), and lists onRestore for any party/ code that calls timers.start. Also edited outside the repo: multiplayer-setup SKILL.md (2 lines) and MODULE-CONTRACTS.md (1 line — rooms games: plain-JSON state, onRestore, keepMatchDays).
- F100 surprise: Cloudflare's own types aren't loaded in a game's tsconfig, so `this.ctx` doesn't exist for tsc in party/worker.ts — the template takes the storage from the constructor's first argument (Glyphtender's Words list does the same).
