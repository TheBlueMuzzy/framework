- F98 CPU — measured: the limit is **10 ms CPU per invocation on Workers Free, and it covers alarms too** (developers.cloudflare.com/workers/platform/limits, updated 2026-10-12: "CPU time per HTTP request: Free 10 ms"; /durable-objects/platform/limits, updated 2026-06-01: DOs follow the plan's per-invocation CPU limit, "each (HTTP request, WebSocket message, or Alarm)"; startup 1 s; 100,000 requests/day). A whole Glyphtender Daily game replayed in the local worker (`wrangler dev --var CHECK_NOW:1`, 12 games of 55–100 moves): **9–18 ms** (Node: 9.2 ms for 72 moves) → over. So "checking…" + the alarm — but one alarm per whole game would hit the same 10 ms, so the alarm replays **10 moves per step** (`MOVES_PER_ALARM`) and keeps the game between steps as JSON: 32 steps measured 1–5 ms (20-move steps: 1–10 ms, too close). The word list is parsed at start-up (1 s budget), not in a request. Local workerd timings are a stand-in for Cloudflare's CPU time (`performance.now()` there only moves on I/O, so a step is a move count, not a time budget).
- F98 security design (from the first brief): score = the replay's only; record version must equal RULES_VERSION; setup must equal `dailySetup(today | yesterday)` (no chosen seeds); body ≤ 100,000 chars + moves ≤ maxMoves, refused unread; names exactly 3 letters A–Z + a short blocked list; player = a random 128-bit id on the device, kept only as a keyed hash, also the proof for "Remove my score" (judgement call: simpler than a separate removal token and just as unguessable); per address (/64 for IPv6) `sendsPerDay` 30 counted BEFORE any check (forged ones count); server-wide 3,000 sends/day (sized to ~20 rows written per checked game vs the free plan's 100,000/day); wrong removals 10/address/day + 2,000 server-wide; all awaits before a synchronous check-count-replay; HMAC with the worker's own secret; old days deleted by the midnight alarm.
