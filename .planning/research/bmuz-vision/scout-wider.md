# Scout: wider AI-dev process ideas BMUZ could borrow (2026-11-08)

Angle: how other AI-coding products and process systems make agents reliable and repeatable, and how they guide non-engineers. Scored against `ARCHITECTURE.md` (the ladder: script / workflow / engine + pipeline / hook) and `VISION.md`.

**How first-hand is this?** Web searches only, no hands-on use of any product. Most hits are secondary write-ups; official docs are marked. Source quality: **A** = official docs or the maker's own post · **B** = solid independent review (Fowler/Thoughtworks, METR) · **C** = blogs, tutorials, vendor marketing · **D** = Reddit/HN anecdotes.

## Part 2 — the top 5

### 1. A checkpoint at every step, and "go back to before X" in plain words
- **Where it comes from:** Replit takes a checkpoint (code + AI context + database) automatically after every request. Rollback is a button by the chat message and shows what will be restored ([docs.replit.com](https://docs.replit.com/help/agent-and-ai), A). Lovable has version history with Restore (C).
- **Evidence it matters:** the biggest complaint from non-coders on Lovable is not knowing whether to restore or start over, and getting stuck in fix loops (D/C, but consistent across sources).
- **BMUZ today:** undo = Esc Esc (this session) or `git revert` (committed). Claude does both, and the creative has no menu.
- **What changes:**
  - The **engine** commits a checkpoint at every step boundary and every gate (script rung).
  - The status band or `/undo` lists the steps in plain words: "1. before 'add jump sound' (14:02) · 2. before 'tune gravity' (14:20)".
  - Picking one runs a revert script that shows what will be undone first (we already do this) and records it in the journal.
- **Vision served:** V2 (no code reading), V16/V19 (nothing lost), V28 (visible).
- **Weighed:** cheap, because it's git commits we mostly make already. The risk is checkpoint noise in the git history, so use a work branch and squash at merge, which /deliver already does.

### 2. A fixed check after every AI step, with a retry cap, then revert-or-escalate
- **Where it comes from:** Stripe blueprints alternate AI steps with fixed-code checks and cap CI retries at 2 rounds before a human sees it (C, widely repeated). 12-Factor Agents: your code owns the stop conditions, retries and budgets (A via C). Temporal: maximum attempts set per step (C). Harness engineering: lint messages carry the fix instructions for the agent (A via C).
- **Evidence it matters:** the Lovable "Try to Fix" loop shows what happens without a cap. METR shows the time going into prompt-review-wait loops.
- **What changes:**
  - Every pipeline step that a workflow runs carries `max_attempts` (default 2) and `on_exhausted: revert_to_checkpoint + log BLOCKED + move on` (this matches CLAUDE.md's "stuck after 3 tries" rule, but enforced by the engine, not remembered).
  - Every check script's failure text says *what to do* ("Type error in Jump.ts:40 — the value can be undefined; guard it or give it a default"), so the AI retry is aimed, not random.
- **Vision served:** V24 (never stalls silently), V7, V35/V39. It also replaces hook rules like GE11 ("3 failed tries").
- **Weighed:** low cost and proven at scale. The case against: some tasks really need more than 2 tries. Handle that with a per-step override in the pipeline data, not a global bump.

### 3. A durable journal: finished steps are never redone, and steps are safe to re-run
- **Where it comes from:** Temporal replays an event history and reads finished steps' results from it instead of redoing them (C/A). LangGraph saves state at each pause, **and on resume the whole step re-runs from its start** (docs.langchain.com, A).
- **Why it matters for our engine:** test 3 in our throwaway proof ("a killed window resumes at the right step") needs exactly this. LangGraph's gotcha will hit us too. If the engine asks at a gate mid-step and the window dies, the step restarts, and anything it did before the question (a commit, a publish) happens twice.
- **What changes:**
  - The pipeline state becomes an **append-only journal** in project files (`.bmuz/journal.jsonl`: step started / output / gate asked / gate answered / deviation / finished). It syncs through git (V27). The deviation log (V8) and the step times (METR point) come for free.
  - Rules for writing steps: **a gate is always its own step**, never in the middle of one. A step with side effects (commit, push, publish) checks the journal first ("already done → skip").
  - "Approved stays approved" (V-section on approvals) becomes literal: a `gate answered` line is never asked again.
- **Weighed:** it's the concept, not the product; Temporal itself is out (a server, so it breaks V2b). A JSONL file plus a reader is small. The case against is one more file format, but it replaces scattered STATE.md notes about where we were.

### 4. A short plan card before building: what, success criteria, out of scope, needs from you
- **Where it comes from:** Replit Plan mode (success criteria + out of scope + steps, then wait) (A). Factory spec mode (acceptance criteria + test plan) (A/C). Kiro's EARS requirements ("When X, the game shall Y") (A/C). Devin's "Required from User" and "Forbidden Actions" sections (A).
- **The caution:** Fowler/Böckeler (B) and the Spec Kit critics (C) say heavy specs for small changes are friction. Every tool here is "spec-first", and none keeps the spec alive afterwards.
- **What changes:**
  - The **task flow** starts by writing a 5-line card from the GDD/TDD: *what the player will see* · *done when* (EARS-style, testable) · *not doing* · *needs from you* · *forbidden*. The **done-check at the end tests the "done when" lines**, so the reviewer judges against the card, not against vibes.
  - The size decides the ceremony: a tweak gets no card, a task gets a card with no gate, a feature gets a card plus the "approve the plan" gate.
  - Keep it spec-*anchored*: when a card changes the design, the plan-check flow updates the GDD/TDD (V16/V19).
- **Vision served:** V1b (the creative approves what they'll *see*), V14, V22, V36.
- **Weighed:** the hand-off card template already exists, so this adds a front half to it. The risk is too many questions (the Spec Kit complaint); the size rule handles it.

### 5. Process evals: test BMUZ itself on replayed scenarios before any core change
- **Where it comes from:** eval-driven development (C). The practitioner rule (Husain/Shankar, via secondary C): **read real failure traces first**, fix the *first* upstream failure, then automate. Anthropic's harness: a JSON feature list with pass/fail per item (A). Harness engineering: automatic checks replaced hand clean-up (A via C).
- **Why it matters:** V11 ("the core is stable; it changes by adding or fixing pieces") needs a way to *prove* a change didn't break something. Today the proof is Muzzy noticing drift weeks later. The ~97 hook rules are effectively evals that were written before anyone did error analysis.
- **What changes:**
  - A `bmuz-evals/` folder of **scenarios**: a scratch project + a scripted creative ("I have an idea for a dice game", "approved", "actually make it blue") + checks on the journal ("define came before code", "gate asked once", "no step skipped without a deviation line", "hand-off card had the next command").
  - Run them headless before releasing a BMUZ update to users (V3: only Muzzy changes it, and every update is tested).
  - Seed them from error analysis: pull the deviation logs and Muzzy's complaints (already mined in `mined-1.md`/`mined-2.md`), tag the *first* failure in each, and write one scenario per failure type.
- **Weighed:** the costliest of the five (headless runs use tokens, and AI judges must be checked against hand labels). But it's the only item that protects V11 over years. Start with 5 scenarios, not 50.

### Honourable mentions
- **Milestone exit criteria as data** (game stage-gates): "alpha = every must in, no P0" in pipeline data feeds /deliver and the PPP %.
- **Limit tools per step** (Roo modes, Factory): a reviewer step has no Edit tool.
- **Load craft skills by file match** (Kiro steering, AGENTS.md size cap): keeps context lean (V13).
- **Autonomy dial in the profile** (Factory): how often a given user wants to be asked.
- **Baseline check at session start** (Anthropic harness): "is the game still working?" before new work.

## Hype vs substance
- **Substance:** checkpoints/rollback (shipped, used daily by millions on Replit/Lovable); bounded retries with fixed-code checks (Stripe at scale); durable journals (Temporal is a mature product); harness engineering (a concrete account from OpenAI's own team).
- **Mixed:** spec-driven development. The idea is sound, but the tools are "spec-first" only and the maker calls Spec Kit an experiment. Take the *card*, not the *ceremony*.
- **Hype or overkill for us:** DSPy optimizers, multi-agent persona theatre (BMAD/CrewAI crews as "teams of experts"), Temporal or LangGraph as actual dependencies (they need servers or Python, which breaks V2b).
- **Unchecked:** Jules, Amp oracle, Cursor background agents, BMAD (no good sources found this pass).
